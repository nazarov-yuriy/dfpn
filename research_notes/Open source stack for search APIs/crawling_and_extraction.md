# Layer: crawling, fetching, rendering and content extraction — what the search-API companies use, the open-source equivalents, and what to learn (as of 2026-11-05)

Method note. Tool budget 30 calls. Prior notes in `../Search API landscape and benchmarks/` (exa.md, keenable.md, wave2_keenable_depth.md, wave2_perplexity_parallel.md, wave2_brave_tavily.md, common_crawl_vs_commercial.md, providers_own_index.md, wave2_newcomers.md) were grepped and their facts reused with their original URLs. New evidence this run (fetched 2026-11-05): crawler.exa.ai; GitHub pages for commoncrawl/nutch, MarginaliaSearch (root and code/readme.md), StractOrg/stract, mwmbl/mwmbl, yacy/yacy_search_server, firecrawl/firecrawl, jina-ai/reader, unclecode/crawl4ai, lightpanda-io/browser, huggingface/datatrove, mlfoundations/dclm, chatnoir-eu/chatnoir-resiliparse, brave/web-discovery-project; Hugging Face cards for jinaai/ReaderLM-v2 and HuggingFaceFW/fineweb-edu-classifier; the trafilatura evaluation page. Failures: GitHub REST API is disabled for this session and GitHub HTML via curl returned nothing, so star/license/last-commit data exist only for repos fetched via WebFetch (GitHub pages do not expose a last-commit date in the fetched text; commit counts are given instead). openwebindex.eu/docs/owler (OWLer crawler docs) rendered empty. Repos marked "(not fetched this run)" are listed from general knowledge for completeness and must be verified before quoting language/license.

Evidence labels: [vendor post] = company blog/docs; [repo] = GitHub/HF page fetched; [talk]/[paper] = conference or arXiv; [independent] = third party with no product in the category; [competitor] = rival vendor; [inferred] = my inference, not stated by anyone.

Headline: no commercial search-API provider has open-sourced its production crawler. What they disclose is (a) crawler identity and politeness policy (Exa, Perplexity, Parallel, Keenable, Brave, Mojeek, Common Crawl), (b) storage/processing frameworks (Exa: Lance on S3 + Ray Data; Common Crawl: Nutch fork on Hadoop with WARC output), and (c) product-level extraction behaviour (markdown output, live-fetch flags, token-reduction claims). The open-source stack that reproduces each layer is well established: Nutch/StormCrawler/Heritrix (Java) or Stract-style Rust crawlers for fetching; Playwright/Puppeteer on Chromium, or Lightpanda, for JS; crawler-commons/google-robotstxt/protego for robots.txt; warcio/FastWARC for WARC; trafilatura/Resiliparse/Readability/jusText and ReaderLM-v2 for main-content extraction; MinHash (datatrove, datasketch, BFF) for dedup; CLD2/fastText for language ID; FineWeb-Edu and DCLM fastText classifiers for quality.

## KQ2. JavaScript rendering

### Takeaway
Only the fetch-and-extract products (Jina Reader: Puppeteer + headless Chrome with curl-impersonate fallback; Firecrawl: managed browser fleet; Crawl4AI: Playwright) disclose JS rendering; Common Crawl explicitly does not execute JavaScript, and no index provider (Exa, Brave, Perplexity, Parallel, Keenable) states whether its index crawler renders. Lightpanda (Zig, AGPL) is the new lightweight alternative, with vendor-measured 16x memory and 9x speed gains over headless Chrome, and Keenable has publicly integrated with it.

### Cited Findings
- Common Crawl: "Currently, JavaScript is not executed and Cookies are not used" — [vendor, CC FAQ](https://commoncrawl.org/faq)
- Jina Reader: pages "rendered with headless Chrome, or fetched lightweight via `curl-impersonate`. Reader picks intelligently between the two"; `x-engine` header forces `browser`, `curl` or `auto` — [repo, jina-ai/reader](https://github.com/jina-ai/reader)
- Firecrawl claims "96% of the web, including JS-heavy pages" and handles "JS-blocked content" with "Rotating proxies"; Actions support click/scroll/write/wait/press before extraction — [repo, firecrawl](https://github.com/firecrawl/firecrawl)
- Crawl4AI: `python -m playwright install --with-deps chromium`; supports Chromium, Firefox, WebKit and remote browsers over CDP — [repo, crawl4ai](https://github.com/unclecode/crawl4ai)

## KQ3. robots.txt, politeness and bot verification

### Takeaway
RFC 9309 compliance is universal in public statements, and 2026 added a second layer: cryptographic bot identity via RFC 9421 HTTP Message Signatures (Exa, Parallel) alongside published IP lists (Perplexity, Keenable, Common Crawl). The disclosed politeness mechanics are per-site rate limits (Exa), Crawl-delay plus adaptive 429/5xx back-off (Common Crawl), and group-precedence rules (Exa follows "major search engine" groups when no ExaSearchBot group exists).

### Cited Findings
- Exa: looks for an ExaSearchBot group first; "If you haven't provided one, it follows the rules you've set for major search engines; otherwise it follows the * group"; "Rate-limited per site to avoid putting load on your servers"; "robots.txt controls crawling, not indexing" (use `noindex`); "does not attempt to bypass logins, paywalls, or CAPTCHAs, and submits no forms" — [vendor, Exa crawler page](https://crawler.exa.ai/)
- Perplexity: PerplexityBot "follows robots.txt limits and, where none are set, industry-standard request rates"; Perplexity-User "generally ignores robots.txt rules" because a user requested the fetch; robots changes take up to 24 h — [vendor, Perplexity bots](https://docs.perplexity.ai/guides/bots)
- Parallel: ShapBot signs with "Web Bot Auth (HTTP Message Signatures, RFC 9421)", key directory at shapbot.parallel.ai; the crawler docs page does not state robots behaviour, while the product page says the crawler "respects robots.txt and related crawling directives" — [vendor, Parallel docs](https://docs.parallel.ai/resources/crawler.md); [vendor, Parallel product page](https://parallel.ai/products/search)
- Keenable: "We follow the Robots Exclusion Protocol (RFC 9309)" — [vendor, Keenable bot page](https://app.keenable.ai/bot)
- Common Crawl: fetches robots.txt first, follows up to 4 redirects (5 for robots.txt), honours `Crawl-delay`, "waits few seconds before sending the next request to the same site", backs off on 429/5xx; UA `CCBot/2.0 (https://commoncrawl.org/faq/)`, reverse DNS under crawl.commoncrawl.org, IP list at index.commoncrawl.org/ccbot.json; politeness causes "Highly ranked domains tend to be underrepresented" — [vendor, CC FAQ](https://commoncrawl.org/faq); [vendor, CCBot page](https://commoncrawl.org/ccbot); [vendor, CC domain stats](https://commoncrawl.github.io/cc-crawl-statistics/plots/domains)

- Firecrawl: "By default, Firecrawl respects robots.txt directives" — [repo, firecrawl](https://github.com/firecrawl/firecrawl); Jina Reader's README does not address robots.txt — [repo, jina-ai/reader](https://github.com/jina-ai/reader)

### Inferences
- [inferred] A new crawler in 2026 needs three identity artefacts to avoid WAF blocks: a documented UA with URL, a published IP list (JSON) or reverse DNS, and RFC 9421 signatures with a `.well-known` key directory; Exa and Parallel are the reference implementations.
- [inferred] Block rates are driven by perceived purpose (AI training vs search); a search-only crawler should say so explicitly on its bot page, as Perplexity ("not used to crawl content for AI foundation models") and Keenable (`KeenableBot` vs the third-party dataset token) do.

## KQ4. WARC tooling and crawl storage

### Takeaway
WARC remains the archival interchange format (Common Crawl, Heritrix, ChatNoir), but production search pipelines convert to columnar text: Exa stores parsed documents in Lance on S3 with a global manifest, Common Crawl publishes a Parquet URL Index beside its WARC files, and FineWeb/DCLM pipelines read WARC once (warcio in datatrove, FastWARC in ChatNoir/DCLM) and never serve it.

### Cited Findings
- Common Crawl formats: WARC (raw HTTP), WAT (metadata and extracted links as JSON), WET (plaintext); October 2026 crawl = 100,000 WARC files, 86.19 TiB compressed; 5 MiB per-fetch truncation since March 2025 — [vendor, CC Get Started](https://commoncrawl.org/get-started); [vendor, October 2026 crawl](https://commoncrawl.org/blog/october-2026-crawl-archive-now-available)
- URL Index (Parquet; renamed from "Columnar Index" on 2026-06-03) with `url`, `content_languages`, `warc_filename`, `warc_record_offset`, `warc_record_length`; `CCIndexWarcExport` pulls records by offset/length; CDXJ server is a pywb deployment, "frequently abused and therefore heavily rate limited" — [vendor, CC blog](https://commoncrawl.org/blog/the-columnar-index-is-now-the-url-index); [repo, cc-index-table](https://github.com/commoncrawl/cc-index-table); [vendor, CC FAQ](https://commoncrawl.org/faq)
- Exa exa-d: Lance format on S3 with a global manifest, Ray Data jobs with embedding models resident in GPU memory — [vendor, Exa](https://exa.ai/blog/exa-d)
- FastWARC: "high-performance WARC parsing library written in Rust with bindings for Python", WARC/1.0 and 1.1, GZip/Zstd/LZ4; Resiliparse adds HTML parsing, encoding and content-type detection, language detection, main-content extraction, and "Process Guards" for time and memory limits; Apache-2.0; 153 stars, 1,717 commits; authors Bevendorff, Stein, Hagen, Potthast (Webis/ChatNoir) — [repo, chatnoir-resiliparse](https://github.com/chatnoir-eu/chatnoir-resiliparse)
- datatrove `io` extra: "dependencies to read warc/arc/wet files and arrow/parquet/Optimized-parquet formats" — [repo, datatrove](https://github.com/huggingface/datatrove)
- ChatNoir stored 28.8 TB of document map files plus a 9.7 TB index for 1.6B CC pages (2018) — [paper, Bevendorff et al. 2018](https://downloads.webis.de/publications/papers/bevendorff_2018.pdf)

### Inferences
- [inferred] Scaling ChatNoir's 2015 ratios to a 2026 crawl implies ~13 TB BM25 index plus ~39 TB document store per snapshot before replication (from common_crawl_vs_commercial.md); storing parsed text in a columnar format (Lance/Parquet) rather than WARC is what makes re-embedding and metadata updates tractable, which Exa cites as a core difficulty.

### Gaps
- warcio, jwarc and cc-pyspark metadata not fetched; FastWARC's speed claim vs warcio exists in its `benchmarks/warc` folder but no numbers were visible.
- Marginalia's crawl storage format in 2026 unverified.

## KQ5. Boilerplate removal, main-content extraction and HTML-to-markdown

### Takeaway
Commercial providers sell extraction as a black box (Exa's "custom HTML parser" and token-cutting extraction models, Keenable's markdown Fetch with optional LLM `prompt`, Brave's "smart chunks", Parallel's "dense excerpts"); the open-source state of the art is trafilatura (F 0.926 on the maintainer's 990-document benchmark, 2026-10-02), with Resiliparse as the throughput option (F 0.811 at 0.3x time), Readability/jusText as the classic heuristics, and Jina's ReaderLM-v2 (1.54B params, cc-by-nc-4.0) as the model-based option.

### Cited Findings
- trafilatura evaluation (2026-10-02, 990 documents, Python 3.13), F-scores: trafilatura 2.3.0 standard 0.926 (2.9x time), precision 0.922, fast 0.920, recall 0.919; magic-html 0.889; justext 3.0.2 0.862 (2.2x); readability-lxml 0.9 0.853 (3.0x); news-please 0.836 (20.9x); resiliparse 1.0.9 0.811 (0.3x); goose3 0.810 (10.6x); boilerpy3 0.807; newspaper4k 0.803; html2text 0.663; raw HTML 0.667; "goose3 is the most precise algorithm, albeit at a significant cost in terms of recall" — [maintainer benchmark, trafilatura docs](https://trafilatura.readthedocs.io/en/latest/evaluation.html)
- FineWeb: WET files "retained too much boilerplate and menu text", so text was extracted from WARC HTML with trafilatura, which produced better models in ablations — [paper, FineWeb](https://arxiv.org/html/2406.17557v2); datatrove: "The most commonly used extractor in datatrove is Trafilatura" — [repo, datatrove](https://github.com/huggingface/datatrove)
- DCLM pools are "unfiltered Common Crawl data that has only undergone text extraction (via resiliparse)" — [repo, dclm](https://github.com/mlfoundations/dclm)
- Jina Reader: `markdown` mode "skips readability"; `x-md-*` options live in `src/dto/turndown-tweakable-options.ts`; PDFs via PDF.js; Office via LibreOffice; VLM-generated alt text via `x-with-generated-alt` — [repo, jina-ai/reader](https://github.com/jina-ai/reader)
- ReaderLM-v2: 1.54B parameters, base Qwen2.5-1.5B-Instruction, up to 512K tokens combined input/output; trained on "html-markdown-1m" with synthetic data from Qwen2.5-32B-Instruction; HTML→Markdown ROUGE-L 0.84, Levenshtein 0.22, Jaro-Winkler 0.82, claimed to outperform Qwen2.5-32B-Instruct and Gemini2-flash-expr; HTML→JSON F1 0.81, Precision 0.82, Recall 0.81, Pass-Rate 0.98; licence cc-by-nc-4.0; 1,127 downloads last month; paper 2025-03-03 — [repo, HF model card](https://huggingface.co/jinaai/ReaderLM-v2); [paper](https://arxiv.org/abs/2503.01151)

- Firecrawl: "Clean markdown"; "Turn PDFs, DOCX, and other documents into clean Markdown or structured JSON"; Agent endpoint takes a Pydantic schema, effort `low|medium|high`, model `spark-2` — [repo, firecrawl](https://github.com/firecrawl/firecrawl)
- Exa: markdown default for `/contents` since 2025-06-23; text-extraction models "reduce LLM token counts by over 20x" (Series C, 2026-05-20); Dynamic Highlights "95% fewer tokens" (2026-10-19) — [vendor, changelog](https://docs.exa.ai/changelog); [vendor, Series C](https://exa.ai/blog/announcing-series-c); [vendor, Exa on AA](https://exa.ai/blog/artificial-analysis-exa-3-best-search-api)

- Parallel returns "dense excerpts" compressed against a natural-language `objective` — [vendor, Parallel](https://parallel.ai/products/search)

### Inferences
- [inferred] The commercial differentiator has moved from extraction (solved to ~0.92 F by trafilatura) to query-conditioned compression (Exa highlights, Keenable Dynamic Snippets, Parallel excerpts, Crawl4AI BM25ContentFilter); a practitioner should treat these as two separate stages.
- [inferred] Resiliparse's 0.3x time at F 0.811 vs trafilatura's 2.9x at 0.926 is the real engineering trade-off at 10^9 pages: DCLM chose Resiliparse for a 300T-token pool, FineWeb chose trafilatura for quality.
- [inferred] ReaderLM-v2's non-commercial licence and ~1.1k monthly downloads indicate it is a research/reference artefact, not what Jina runs in production at 100 RPM; Reader's production path is Puppeteer + Readability-style + Turndown.

### Gaps
- trafilatura's licence and star count were not fetched (the evaluation page carries no licence statement).
- No commercial provider publishes extraction accuracy; "20x" and "95%" are vendor token-reduction claims, not extraction-quality measurements.
- Turndown, html-to-markdown (Go), MarkItDown, Mozilla Readability metadata not fetched this run.

## KQ6. Deduplication, language identification and quality filtering

### Takeaway
The open-source LLM-data pipelines (FineWeb/datatrove, DCLM) are the only fully documented implementations: MinHash per snapshot (FineWeb) or Bloom-filter fuzzy dedup in Rust (DCLM's BFF), fastText language ID, Gopher/C4/RefinedWeb heuristics, and learned quality classifiers (FineWeb-Edu's Snowflake-arctic-embed-m head, F1 0.82 at threshold 3; DCLM's OH2.5+ELI5 fastText). Common Crawl uses CLD2 in its Nutch fetcher and harmonic centrality for crawl-time quality; no commercial search provider discloses any of these components.

### Cited Findings
- FineWeb: base filtering ~36T tokens → per-snapshot MinHash ~20T → heuristics remove a further ~22% → ~15T; global dedup across 96 snapshots removed up to 90% of the oldest snapshots and lowered quality; FineWeb-Edu classifier run over 15T tokens cost ~6,000 H100 GPU-hours — [paper, FineWeb](https://arxiv.org/html/2406.17557v2)
- FineWeb-Edu classifier: "We added a classification head with a single regression output to" Snowflake-arctic-embed-m; ~450k annotations by Llama3-70B-instruct on a 0–5 scale; 20 epochs, lr 3e-4, encoder frozen; recommended threshold `int_score >= 3`; F1 82% as a binary classifier; accuracy 0.71 on a 46,867-sample hold-out; apache-2.0; limitations: "focused on educational content relevant to primary and grade school levels", "might overfit to academic looking content" — [repo, HF model card](https://huggingface.co/HuggingFaceFW/fineweb-edu-classifier)
- datatrove: Apache-2.0, 3.4k stars, 328 forks, 762 commits, Python 3.11+; dedup examples for MinHash, sentence-level exact dedup and ExactSubstr; executors Local, Slurm, Ray, HF Jobs (experimental); `fineweb.py` is a "full reproduction of the FineWeb dataset"; `fasttext_{language}` stat — [repo, datatrove](https://github.com/huggingface/datatrove)
- DCLM: MIT, 1.5k stars; "a standardized corpus of over 300T unfiltered tokens from CommonCrawl"; DCLM-Baseline uses BFF, "a Rust tool for inter-document fuzzy deduplication", and an "OH2.5 + ELI5" fastText filter (the step DCLM-RefinedWeb omits); processing "relies on Ray"; pool sizes 7B-1x 7.85T, 7B-2x 15.7T tokens — [repo, dclm](https://github.com/mlfoundations/dclm); [paper](https://arxiv.org/abs/2406.11794)
- Common Crawl: CLD2 language detection in the Nutch fetcher; language stats (CLD2 primary language) for CC-MAIN-2026-43: English 42.56%, Russian 6.30%, German 5.77%, Japanese 4.89%, French 4.76%, Spanish 4.74%, Chinese 4.37% — [repo, commoncrawl/nutch](https://github.com/commoncrawl/nutch); [vendor, CC language stats](https://commoncrawl.github.io/cc-crawl-statistics/plots/languages)
- Common Crawl crawl-time quality: harmonic centrality chosen over PageRank because "it is deemed better at avoiding spam"; director: "If we were to 10X that, we believe the quality would drop because we're going into lower ranked pages"; spam traps handled by heuristics plus manual intervention — [independent, Mozilla Foundation 2024](https://assets.mofoprod.net/network/documents/Common_Crawl_Mozilla_Foundation_2024.pdf); [vendor, CC webgraph stats](https://commoncrawl.github.io/cc-webgraph-statistics/)
- Exa: "most crawled documents are low quality so selecting good URLs is central" — [vendor, Exa](https://exa.ai/blog/how-to-build-nextgen-search)
- Resiliparse includes language detection and encoding detection modules — [repo, chatnoir-resiliparse](https://github.com/chatnoir-eu/chatnoir-resiliparse)

### Inferences
- [inferred] For a search index (as opposed to a training corpus) dedup must be near-duplicate at URL and content level simultaneously (mirrors, tracking parameters, pagination); FineWeb's warning against global dedup is less relevant because an index keeps one copy by design, but it shows that dedup thresholds materially change corpus composition.
- [inferred] Commercial providers almost certainly run the same cost ladder (heuristics → fastText → embedding classifier) but disclose nothing; Exa's "selecting good URLs" statement implies crawl-time prioritisation (graph/quality scores) rather than post-hoc filtering only.

### Gaps
- datatrove's individual filter blocks (Gopher, C4, FineWeb quality, URL filters) are in the source tree but not enumerated in the README fetched.
- DCLM's fastText training-set composition and the "f0.15" keep fraction are in the paper, not the README; not fetched this run.
- datasketch, deduplicate-text-datasets, text-dedup, CLD2 and fastText repos not fetched this run.
- No commercial provider discloses dedup, language-ID or quality-classifier methods.

## KQ7. PDF extraction, sitemaps/feed discovery and recrawl scheduling

### Takeaway
PDF handling is disclosed only by the fetch products (Jina: PDF.js and LibreOffice; Firecrawl: PDF/DOCX to markdown and a `pdf` search category); URL discovery is sitemaps-from-robots.txt plus prior crawls for Common Crawl, browser telemetry for Brave, and undisclosed for everyone else; recrawl policy is uniformly "adaptive" in vendor language (Exa change detection with content-type tiers, Perplexity ML-scheduled, Parallel "intelligently recrawled", Brave 100M+ pages/day) against Common Crawl's monthly ~50%-revisit snapshots and Marginalia's ~5-day full crawl.

### Cited Findings
- Jina Reader: "any URL ending in `.pdf` is parsed with PDF.js and returned as markdown"; Office files "converted via LibreOffice and then processed as HTML/PDF" — [repo, jina-ai/reader](https://github.com/jina-ai/reader)
- Firecrawl: PDFs and DOCX to markdown; `/search` categories include `pdf`, and `research` moves to a PubMed/arXiv "Research Index" on 2026-11-16; PDF scraping 1 credit/page — [repo, firecrawl](https://github.com/firecrawl/firecrawl); [vendor, Firecrawl billing](https://docs.firecrawl.dev/billing)
- Common Crawl collects HTML only, "generally not CSS, images or media"; "CCBot uses sitemaps announced in robots.txt"; CrawlDB expanded from prior crawls, separate discovery crawls and sitemaps — [independent, Mozilla 2024](https://assets.mofoprod.net/network/documents/Common_Crawl_Mozilla_Foundation_2024.pdf); [vendor, CC FAQ](https://commoncrawl.org/faq)
- Brave Web Discovery Project: extension sends `query` messages (SERP visits) and `page` messages (visited URLs) — [repo, brave/web-discovery-project](https://github.com/brave/web-discovery-project); Brave: index "powered by real queries and clicks in the Brave browser" — [vendor, Brave](https://brave.com/search/api/guides/what-sets-brave-search-api-apart/)
- Crawl4AI `AsyncUrlSeeder` seeds from sitemaps and Common Crawl ("a pre-built index of the internet"); `prefetch=True` "finds URLs 5 to 10 times faster" — [repo, crawl4ai](https://github.com/unclecode/crawl4ai); [vendor docs, Crawl4AI URL seeding](https://docs.crawl4ai.com/core/url-seeding/)
- Exa recrawl: "crawlers detect changes and regenerate embeddings before a query arrives"; update frequency varies ("news hourly, some papers never"); FAQ: pages "discovered and refreshed continuously," no fixed recrawl schedule; `maxAgeHours` replaced `livecrawl` 2026-02-02 — [vendor, exa-d](https://exa.ai/blog/exa-d); [vendor, Exa FAQ](https://exa.ai/docs/admin/faqs.md); [vendor, changelog](https://docs.exa.ai/changelog)
- Perplexity: ML-scheduled recrawl, "tens of thousands of indexing operations per second" (2025-09-25) — [vendor, Perplexity](https://www.perplexity.ai/hub/blog/architecting-and-evaluating-an-ai-first-search-api)
- Brave: "we add or refresh more than 100 million pages each day" on 40B pages (2026-02-24) — [vendor, Brave](https://brave.com/blog/search-api-growth/)
- Parallel: "Intelligently recrawled to keep data fresh"; freshness policies set page-age triggers for live crawls; "Millions of pages added daily" — [vendor, Parallel](https://parallel.ai/products/search)
- Keenable: results carry `acquired_at`; Fetch `live` flag "required for unindexed URLs"; point-in-time `query_time`; news queries generated hourly in NEEDLE implying at-least-hourly news ingestion — [vendor, Keenable Fetch](https://docs.keenable.ai/api-reference/fetch.md); [vendor, NEEDLE post](https://keenable.ai/blog/needle-the-benchmark-your-search-engine-can-t-memorize)
- You.com: source modes `blend` (default), `cache`, `fetch`; "Only pages crawled live are billed"; "cache coverage varies by how recently pages were crawled" — [vendor, You.com billing](https://you.com/docs/administration/billing)
- Common Crawl: "about 50% of each crawl is made up of URLs that have been fetched in previous crawls"; captures "discontinuous"; selection adds bonuses/penalties by time since last successful fetch — [independent, Mozilla 2024](https://assets.mofoprod.net/network/documents/Common_Crawl_Mozilla_Foundation_2024.pdf)
- Marginalia: full crawl took "nearly four months" before July 2026, now ~5 days plus ~1 week time-based crawl of wide domains (tumblr.com 8,450,330 known subdomains) — [vendor blog, Marginalia 2026-07-22](https://www.marginalia.nu/log/a_138_systemdocker/)
- Open Web Index: "we crawl on a daily basis ... index delta files ... at daily intervals" — [paper, Hendriksen et al. 2024](https://elib.dlr.de/210780/1/hendriksen_2024.pdf)
- YaCy: crawler "with a scheduler to keep a search index fresh" — [repo, yacy](https://github.com/yacy/yacy_search_server)

### Inferences
- [inferred] Every API now exposes freshness as a user-controlled knob (Exa `maxAgeHours`, Tavily `max_age_hours`, You.com `fetch`, Keenable `live`, Parallel page-age triggers), which shifts recrawl cost to the caller for the tail and lets the index crawler focus on high-change-rate content; an open-source clone should implement "serve-from-index unless older than N hours, else live-fetch" as a first-class policy.
- [inferred] Brave's 100M+/day on 40B pages implies a mean revisit interval of roughly 400 days if spread uniformly; the actual policy must be heavily tiered (arithmetic on vendor figures, not a disclosed number).

### Gaps
- No provider publishes a recrawl algorithm, change-rate model or SLA; "ML-scheduled" (Perplexity) and "intelligently" (Parallel) are unquantified.
- PDF extraction libraries (PyMuPDF, pdfplumber, Docling, Marker, MinerU, olmOCR, Tika/PDFBox) and sitemap/feed libraries (crawler-commons, ultimate-sitemap-parser, feedparser, courlan) were not fetched this run; Nutch `AdaptiveFetchSchedule` and the Cho & Garcia-Molina refresh-policy literature were not fetched.
- Exa's PDF/paper ingestion pipeline is undisclosed despite "papers" being named as a content tier.

## Learning path for this layer (ordered)

1. **Crawl loop fundamentals**: read Apache Nutch's Injector → Generator → Fetcher → Parse → UpdateDB cycle and Common Crawl's fork (`Generator2`, WARC-in-Fetcher, CLD2) — https://github.com/commoncrawl/nutch; then the Mozilla report's CrawlDB/harmonic-centrality description — https://assets.mofoprod.net/network/documents/Common_Crawl_Mozilla_Foundation_2024.pdf.
2. **A modern single-team design**: Marginalia's crawling/converting/loading processes and its 2025–2026 blog posts on crawler politeness and 5-day full crawls — https://github.com/MarginaliaSearch/MarginaliaSearch, https://www.marginalia.nu/log/; Stract's archived Rust codebase for a Tantivy-backed engine — https://github.com/StractOrg/stract.
3. **Bot identity and politeness**: RFC 9309 group precedence as implemented by Exa — https://crawler.exa.ai/; RFC 9421 Web Bot Auth as deployed by Exa and Parallel — https://docs.parallel.ai/resources/crawler.md; Common Crawl's back-off and IP publication — https://commoncrawl.org/faq. Implement with crawler-commons (Java) or google/robotstxt (C++) or protego (Python) (verify licences).
4. **WARC and columnar storage**: warcio/FastWARC for reading, Common Crawl's URL Index (Parquet) for lookups, Lance (Exa) or Parquet for parsed text — https://github.com/chatnoir-eu/chatnoir-resiliparse, https://commoncrawl.org/blog/the-columnar-index-is-now-the-url-index, https://exa.ai/blog/exa-d.
5. **Rendering**: Playwright/Puppeteer on Chromium for correctness, Lightpanda for cost (verify its vendor benchmark), curl-impersonate for the lightweight path, with Jina Reader's `auto` engine selection as the pattern — https://github.com/jina-ai/reader, https://github.com/lightpanda-io/browser.
6. **Extraction**: trafilatura (quality) and Resiliparse (throughput), with Readability/jusText as reference heuristics; measure on your own domain mix using the trafilatura benchmark method — https://trafilatura.readthedocs.io/en/latest/evaluation.html; then query-conditioned compression (Crawl4AI `BM25ContentFilter`) as a separate stage — https://github.com/unclecode/crawl4ai; ReaderLM-v2 as the LLM-based reference — https://huggingface.co/jinaai/ReaderLM-v2.
7. **Dedup, language ID, quality**: reproduce FineWeb with datatrove (MinHash, fastText, Gopher/C4 filters, FineWeb-Edu classifier) — https://github.com/huggingface/datatrove, https://huggingface.co/HuggingFaceFW/fineweb-edu-classifier; study DCLM's Resiliparse + BFF + fastText pipeline on Ray — https://github.com/mlfoundations/dclm.
8. **Recrawl and freshness semantics**: design two agents (index crawler vs user fetcher) and a "max age" policy as exposed by Exa, Keenable, You.com and Parallel; study Common Crawl's revisit statistics and Marginalia's crawl cadence as the two open reference points.
