# Indexing and first-stage retrieval: what the search-API companies use and the open-source equivalents

Scope: the index/retrieval layer only (inverted-index engines, dense retrieval and ANN, embedding models, learned sparse, late interaction, hybrid fusion, sharding/compression/index-build, web graphs). Research date: 2026-11-05. Evidence labels: [vendor post], [vendor case study], [repo], [paper], [talk], [prior note] (fact reused from `research_notes/Search API landscape and benchmarks/*.md`), [inferred], [background] (widely known fact not re-verified in this run). Repo stars, licence and last-commit values come from shields.io badge JSON fetched 2026-11-05 (GitHub's API and HTML were blocked for this session); shields returns the top-language share but not its name, so language names are from the fetched READMEs/Cargo files where stated and otherwise [background]. Hugging Face download/like/licence figures are from the HF models API fetched 2026-11-05. Vendor figures are claims, never measurements.

## KQ1. Component map: who uses what, and the open-source equivalents

### Takeaway
Only four providers disclose their first-stage retrieval engine in any technical detail: Exa (custom Rust/C++ clustered binary-quantized vector DB plus a custom Rust BM25 index, fused with RRF), Perplexity (built on Vespa, later moved its web index to a purpose-built internal system per Vespa's own case study), Brave (lineage from Cliqz/Tailcat: query-based "page models" keyed by query n-grams in Keyvi/RocksDB/Cassandra with Granne vectors, not a classic inverted index) and the open engines (ChatNoir on Elasticsearch; Stract on a vendored tantivy fork; Marginalia on a custom Java two-tier inverted + forward index; Mwmbl on a 4 KiB-page hashed Python/Rust index; OWI on CIFF+Parquet; Common Crawl on CDXJ + Parquet URL lookups, not full text). Keenable, Parallel, Tavily, Linkup, Firecrawl, Jina, You.com, Octen, Ceramic, Mojeek and Kagi publish nothing checkable about their index data structures.

### Inferences
- The disclosed commercial designs converge on "custom engine in Rust/C++ for the web index, hybrid dense+lexical candidates, learned reranking afterwards"; Exa writes its own, Perplexity started on Vespa and then (per Vespa) went custom, and Brave inherited Cliqz's query-model index. No provider in scope is documented running Elasticsearch, Solr or a hosted vector database for its web index. [inferred]
- The closest open-source analogue to Exa's vector DB is FAISS-style IVF with binary/PQ codes plus full-precision rerank, not HNSW; Exa itself says it rejected HNSW for filterability and sharding. [inferred from the 2024-12-17 post]
- Exa's storage choice (Lance on S3) means LanceDB/Lance is the one open component Exa has publicly said it uses in production. [inferred from the exa-d post]

## KQ2. Inverted-index engines: what the evidence actually says about each

### Takeaway
Exa's own BM25 index is the best-documented commercial lexical index (1.8 TB/1B docs baseline, >50% cut via d-gap/varint, TF bitmaps and zstd), ChatNoir is the only documented Elasticsearch web index (124 nodes for 3B docs, 2018), and the small open engines each hand-roll a lexical index (Stract: vendored tantivy; Marginalia: two-tier Java index; Mwmbl: hashed 4 KiB pages) rather than running Elasticsearch/Solr.

### Cited Findings
- Exa BM25 baseline "over 1.8TB per 1 billion indexed documents across distributed workers"; sorted doc IDs delta-encoded with variable-length encoding "reduced the average overhead from 4 bytes to 1.3 bytes"; term frequencies grouped and stored as a 2-byte bitmap over the 1–15 range; zstd applied over entire lists because queries scan whole lists; per-token `Vec` replaced by `(offset, len)` pointers cutting header "from 24 bytes" to 8; singleton tokens stored as a bare doc ID; average latency "dropped by 10%"; retrieval uses rarest-term (highest-IDF) candidate selection and WAND-inspired pruning with "sub-500ms latencies to retrieve 1000s of top results"; implementation in Rust; author Tom An, 2025-05-05 — [Exa](https://exa.ai/blog/bm25-optimization) [vendor post]
- ChatNoir (2018): ClueWeb09 734.8M + ClueWeb12 638.8M + CC 11/2015 1.6B = 3.0B docs; 130-node cluster (124 Elasticsearch data nodes); 40 primary shards per corpus, replication 3; CC index 9.7 TB (29.2 TB replicated) plus 28.8 TB document map; ~600 ms warm / ~2,100 ms cold; ≥20,000 docs/s indexing; BM25 with Boolean prefilter then top-400-per-shard rescoring — [Bevendorff et al., ECIR 2018](https://downloads.webis.de/publications/papers/bevendorff_2018.pdf) [paper; prior note]
- Stract workspace: `tantivy = { path = "crates/tantivy" }` (a vendored copy, no crates.io version), members include `crates/tantivy`, `crates/speedy-kv`, `crates/file-store`, `crates/simple-wal`, `crates/robotstxt`, `crates/web-spell`; `openraft = { version = "0.9.1" }`, `scylla = "0.12.0"`, `redb = "2.0.0"`, `candle-* = "0.3.3"`, `tokenizers = "0.13.2"`; package licence AGPL-3.0 — [Cargo.toml](https://github.com/StractOrg/stract/blob/main/Cargo.toml); [core Cargo.toml](https://github.com/StractOrg/stract/blob/main/crates/core/Cargo.toml) [repo, fetched 2026-11-05]; repo 2.4k stars, last commit March 2025, archived 2026-04-02 — [shields.io, fetched 2026-11-05](https://img.shields.io/github/last-commit/StractOrg/stract.json); [prior note](https://github.com/StractOrg/stract)

## KQ3. Dense retrieval and ANN against Exa's custom vector database

### Takeaway
Exa's documented design (Matryoshka 256-d, 1-bit binary quantization, 100k-cluster IVF, register-resident lookup tables, full-precision rerank, inverted indexes for filters) maps onto FAISS IVF + binary/PQ codes rather than HNSW, and Perplexity's Vespa case study independently reports rejecting stand-alone vector databases for filter reliability; Cliqz/Brave used 200-d vectors in Granne as one of several matchers.

### Cited Findings
- Exa requirements and techniques: "billions of 4096-float vectors", metadata filters, <100 ms, >500 QPS; Matryoshka truncation to 256 dims (20x memory cut); binary quantization to 1 bit/dim (16x more); asymmetric dot product with 4-dim subvector lookup tables kept in CPU registers, hot path in C++ rather than Rust; 100,000 clusters searched by nearest cluster (~1000x throughput); rerank of extra candidates with uncompressed vectors; inverted indexes on category/date/domain/keyword so search runs only over the filtered set; clustering preferred over HNSW for filters and sharding; ~10x cheaper than cloud vector-DB quotes — [Exa, 2024-12-17](https://exa.ai/blog/building-web-scale-vector-db) [vendor post; prior note]
- Exa 2.0: vector DB "updated with new clustering algorithms, lexical compression, and assembly optimizations in Rust" — [Exa, 2025-10-10](https://exa.ai/blog/exa-api-2-0) [vendor post; prior note]
- Exa data layer: Lance format on S3 with global manifest; Ray Data jobs; "hundreds of billions of pages, petabytes of raw content" — [Exa exa-d, 2026-01-13](https://exa.ai/blog/exa-d) [vendor post; prior note]
- Exa query DAG: "query embedding → token-level ANN worker group (replicated encoders/scorers)" — [Exa, 2026-04-17](https://exa.ai/blog/composing-a-search-engine) [vendor post; prior note]
- Perplexity on Vespa: vector databases "could not reliably handle even simple boolean filters"; needed "keyword and semantic search, structured filtering, passage-level ranking, and continuous indexing in one engine"; "later moved its web index to a purpose-built internal search system but still uses Vespa for other use cases"; 780M+ queries/month, 20%+ monthly growth — [Vespa case study, undated, © 2026](https://vespa.ai/perplexity/) [vendor case study]
- Cliqz: "Vectors are 200-dimensional and indexed with Granne"; storage split across Keyvi, Granne, RocksDB and Cassandra "chosen by mutability, latency, and compression needs"; total index ~50 TB — [0x65.dev, 2019-12-06](https://0x65.dev/blog/2019-12-06/building-a-search-engine-from-scratch.html) [vendor engineering post]
- Open ANN activity (shields.io, 2026-11-05): FAISS 41k/MIT/2026-11-04; hnswlib 5.4k/Apache-2.0/Sep 2026; DiskANN 2k/MIT/2026-11-05; Lance 7.3k/Apache-2.0/2026-11-05; LanceDB 12k/Apache-2.0/2026-11-05; Milvus 47k/Apache-2.0/2026-11-05; Qdrant 35k/Apache-2.0/Oct 2026; Weaviate 17k/2026-11-04; pgvector 24k/2026-11-05; ann-benchmarks 5.7k/MIT/Jul 2026 — e.g. [FAISS badge](https://img.shields.io/github/stars/facebookresearch/faiss.json)

### Inferences
- Memory arithmetic on Exa's stated parameters: a 4096-d float32 vector is 16 KB; 256-d binary is 32 bytes, a 512x reduction; at Exa's claimed 100B pages served (Oct 2026, vendor) that is ~3.2 TB of binary codes plus cluster/ID overhead — consistent with Exa's "less than a gaming PC" memory remark for the earlier billions-scale index, but this is arithmetic on vendor numbers, not a measurement.
- Both Exa (filters, sharding) and Perplexity (boolean filters) cite filtered search as the reason to avoid off-the-shelf HNSW vector databases; a practitioner building web-scale retrieval should learn IVF-style partitioning with per-partition filters, which FAISS and Vespa expose, rather than pure HNSW.

### Gaps
- Exa does not disclose cluster assignment method, re-clustering cadence, or how 256-d binary codes interact with the "token-level" ANN workers mentioned in 2026.
- No open benchmark compares Exa-style IVF+binary against DiskANN/HNSW on web-scale filtered workloads.
- Granne (Cliqz's ANN library) was not fetched; its current maintenance status is unknown.

## KQ5. Learned sparse, late interaction and hybrid fusion

### Takeaway
RRF with k=60 over a BM25 node and a dense ANN node is the one fusion method a provider (Exa) has documented; Perplexity describes hybrid candidate merging without naming the method; no provider documents SPLADE; late interaction appears only as Jina v4's multi-vector output and, suggestively, Exa's "token-level ANN worker group".

### Cited Findings
- Exa: "a sparse retrieval node on an inverted index fused with dense results via reciprocal rank fusion (k=60), domain-diversity step, safe-search filter, two rerankers (relevance and authority)"; ~250 ms serving — [Exa, 2026-04-17](https://exa.ai/blog/composing-a-search-engine) [vendor post; prior note]

## KQ8. Learning path for the indexing and first-stage retrieval layer

### Takeaway
Learn the lexical engine internals first (Lucene/tantivy segments, postings compression, BM25, WAND), then IVF/PQ/binary ANN with filters (FAISS, Vespa), then embedding training and evaluation (FlagEmbedding, MTEB), then fusion and multi-vector methods, then web graphs; Exa's four engineering posts plus the Cliqz 2019 post are the best public descriptions of a production design.

### Cited Findings (ordered path, each item points at the evidence that motivates it)
1. Inverted-index fundamentals in a readable codebase: tantivy (Rust, MIT, 16k stars) and Lucene (Java, Apache-2.0); then PISA for compression research and Anserini/Pyserini for reproducible BM25 baselines — repo stats [shields.io, 2026-11-05](https://img.shields.io/github/stars/quickwit-oss/tantivy.json); CIFF to move indexes between them — [osirrc/ciff](https://github.com/osirrc/ciff)
2. Postings compression and pruning as practised in production: d-gaps + varint, TF bitmaps, zstd, WAND — [Exa, 2025-05-05](https://exa.ai/blog/bm25-optimization)
3. Clustered/quantized ANN with filters: Matryoshka + binary quantization + IVF + register LUTs + full-precision rerank — [Exa, 2024-12-17](https://exa.ai/blog/building-web-scale-vector-db); open implementation surface in FAISS and Vespa; why pure vector DBs were rejected — [Vespa case study](https://vespa.ai/perplexity/)
4. One-engine hybrid stacks: Vespa (keyword + vector + filters + ML inference) as the open analogue of what Perplexity chose — [Vespa case study](https://vespa.ai/perplexity/); Elasticsearch/OpenSearch RRF [background]
5. ### Inferences
- Rust is the common language of the disclosed modern designs (Exa's BM25 and most of its vector DB, Stract, tantivy/Quickwit, Qdrant, Lance, Meilisearch) with C++ for hot paths (Exa, FAISS, Keyvi, Typesense, PISA) and Java for the older/academic stack (Lucene, Elasticsearch, Vespa, Marginalia, cc-webgraph); a practitioner targeting this layer should be fluent in Rust and able to read C++ and Java.

### Gaps
- No public course or textbook-style resource from any provider; the learning path above is assembled from engineering posts and repos, not from a provider-published curriculum.
