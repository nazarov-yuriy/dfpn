## KQ1. What have founders Andrey Styskin and Matthias Petri said publicly about how the index, crawler and ranker work?

### Takeaway
The founders have said very little that is mechanistic. The most concrete public statements are Styskin's TechCrunch quotes (2026-08-25) that the cost of "scanning the whole internet" is "enormous" so the trick is to "narrow the search space based on your query very fast" using index structures tuned per task, plus the blog line "We built Keenable as a learning machine" and a shipping timeline. No talk, podcast, LinkedIn post or HN comment by either founder explaining ranking or crawling mechanics was found.

### Cited Findings
- **[journalist, 2026-08-25]** TechCrunch (Anna Heim) quotes Styskin: "This actually creates a new flywheel that is different from what Google learned from human behavior"; "the cost of serving and scanning the whole internet is enormous because of the volume"; "That's why you need to innovate on how you can narrow the search space based on your query very fast"; "This is what we are bringing to the table." On the cost of building the index: "Don't ask — it is painfully expensive." Styskin calls moving users off Google "extremely hard" but says Google is "beatable" on agentic queries. — [TechCrunch](https://techcrunch.com/2026/08/25/accel-backed-keenable-is-indexing-the-web-for-ai-agents/)
- **[journalist, 2026-08-25]** TechCrunch paraphrases Styskin: without tuning index structures for a specific task, serving and scanning the web is very costly; Keenable's approach is to narrow the search space quickly based on the query. ### Inferences
- The only mechanistic hint from the founders is "narrow the search space based on your query very fast" plus "tuning index structures for a specific task" (TechCrunch paraphrase). Read together with the "learning machine" and "flywheel from agent behaviour" lines, the stated design is: an owned 100B-scale index whose candidate-generation structures are specialised per query/task type, with agent traffic (not human clicks) as the training signal.
- If the Rankless profile is the same Matthias Petri (co-author set Gog/Moffat/Mackenzie is the Melbourne compressed-index / succinct-data-structure group), the chief scientist's research background is in inverted-index compression and efficient query processing, which is consistent with the latency-first positioning. This is an inference, not a sourced fact.
- "Built the web grounding service behind Alexa" (homepage) suggests prior production experience with sub-second grounding for voice, which matches the Gradium voice-agent positioning and the sub-250ms targets.

### Gaps
- No talks, podcasts, conference slides, LinkedIn posts or X posts by Styskin or Petri were found. WebSearch for `"Styskin" OR "Matthias Petri" Keenable ... interview` returned only unrelated academics; Bing returned one unrelated result; LinkedIn and X were not fetchable in-session.
- Neither founder has publicly stated whether first-stage retrieval is lexical (inverted index), dense (ANN over embeddings) or hybrid, what the ranker is trained on, or how the crawler prioritises URLs.
- The Accel note's claim that Styskin "built a 200-billion-document web index at Yandex" is an investor statement with no independent corroboration found.

## KQ2. What do Keenable's own blog posts say, in full and with dates?

### Takeaway
Eight posts exist (Jul 26 – Oct 20, 2026). The two with technical substance are Dynamic Snippets (2026-10-15: a query-conditioned token classifier with published thresholds, halving search-result tokens and lifting BrowseComp accuracy 56.6%→67.3% in vendor runs) and NEEDLE (2026-08-27: the "learning machine" argument and p50 200ms claim). SELECT (2026-09-03) describes a LOTUS-style semantic-SQL layer over search results. No post describes crawler or index structure; no post titled "per-task index structures" or "latency engineering" exists. All post pages carry a conflicting "Nov 3, 2026" metadata stamp.

### Cited Findings
- **[vendor, fetched 2026-11-05]** Blog index (landing.keenable.ai/blog 301-redirects to keenable.ai/blog) lists eight posts: "Keenable ranks #1 on the Vals Web Search Index" (Oct 20, 2026; byline "Vals, Keenable"); "Introducing Dynamic Snippets: 50% Fewer Tokens for Agentic Search" (Oct 15, 2026; Matthias Petri, Ilya Gusev); "cognee's agent memory now reads the web through Keenable" (Sep 22, 2026; Keenable Team); "Keenable partners with Baseten to make web search native to inference" (Sep 16, 2026; Andrey Styskin); "SELECT the tail FROM the web" (Sep 3, 2026; Ilya Gusev, Matthias Petri, Andrey Styskin); "Keenable now runs inside Lightpanda" (Aug 28, 2026; Keenable Team); "NEEDLE: The benchmark your search engine can't memorize" (Aug 27, 2026; Gusev, Petri, Styskin); "Natural conversation, live retrieval: Keenable search with Gradium" (Jul 26, 2026; Keenable Team). — [keenable.ai/blog](https://keenable.ai/blog)
- **[vendor, 2026-10-15] Dynamic Snippets, mechanism:** the document is split into overlapping chunks; a token classifier reads the query together with one chunk and assigns each token a probability of being useful for that query; the classifier is "trained on real search needs and agent trajectories, labeled with the facts and evidence needed to answer complex questions". Decoding: m = highest token score in the document; θ_run = max(α·m, 0.5), θ_peak = β·m, production α = 0.6, β = 0.75; (1) maximal runs with score ≥ θ_run become candidate spans, (2) a run is kept only if some token reaches θ_peak, (3) runs < g = 80 characters apart are joined. Fallback when no token reaches θ_run: the 200 characters centred on the top token, used for ~4% of documents. Snippets have no fixed length target. The post does not name the classifier architecture nor say explicitly whether scoring runs at index time or query time (query-conditioning implies query time). — [Keenable blog](https://keenable.ai/blog/keenable-snippets-full-page-cost-reduction)
- **[vendor, 2026-10-15] Dynamic Snippets, numbers:** production responses averaged 135 KiB before rollout and 69 KiB after, "49% smaller"; on public benchmarks agents read "28–60% fewer search-result tokens per question" and score higher; BrowseComp search-result tokens per question fell "from 1.16M to 466k" and accuracy "rises from 56.6% to 67.3%"; Keenable uses fewer tokens per question than Exa and Parallel on all three benchmarks and has the highest accuracy on BrowseComp and AA-Omniscience (third benchmark not named in extracted text). Harness: Artificial Analysis Search API setup, Stirrup harness, GPT-5.6 Luna answer model, 25-turn limit, two tools (search under test + simple fetch). Snippets "add no latency" and are on by default in the realtime API, which has "p95 latency of 200ms". — [Keenable blog](https://keenable.ai/blog/keenable-snippets-full-page-cost-reduction)
- **[vendor, 2026-08-27] NEEDLE post, methodology and argument:** static benchmarks like BrowseComp suffer overfitting, memorisation and leakage ("agents have pulled answer keys from HuggingFace"); NEEDLE "runs continuously in public" with five query types (News, Finance, Scholar, AgenticRare, Legal); News queries "generated hourly from curated RSS feeds and Google Trends"; "Every task is re-run daily or hourly on a new slice of queries"; the "ultimate" engine "keeps the best results found by any engine in the comparison, ranked by the same judge that scores them all"; overlap and shared-mistake rate are combined into one chart ("What they shouldn't share is mistakes"); data sources Wikidata, GLEIF, SEC XBRL, DeepResearchGym, LRAT, OpenResearcher logs; engines compared Google (Serper), Bing (SearchAPI), Brave, Tavily, Parallel, Exa. Rare-entity queries from agent logs are "closest to real agentic traffic" and show the largest gap between delivered and achievable quality. External figures cited: ~14M agentic requests in a SIGIR'26 study; agents make ~3x fewer spelling errors than humans (ASQ authors). — [Keenable blog](https://keenable.ai/blog/needle-the-benchmark-your-search-engine-can-t-memorize)
- **[vendor, 2026-09-03] SELECT post:** "an agentic tool that queries the web as a database"; the agent declares a slice of the web and the fields it wants; the system "materializes only what the agent's query actually needs"; semantic operators "accept prompts executed by an LLM over some database column", credited to the LOTUS filter/map/join/top-k formalism; output is a "typed, cited table"; "WebQL did the work of turning unstructured pages into rows"; evaluated on WideSearch and WANDR with GPT-5.6-Sol (medium) in a ReAct loop with planning and history compression; 12 WideSearch samples found contaminated via HuggingFace downloads and re-run with HF blocked. The named functions SEM_EXTRACT / SEM_MATCH / SEM_NORM appear on the homepage, not in this post. No page-count, index, crawl or latency statements. — [Keenable blog](https://keenable.ai/blog/select-the-tail-from-the-web)
- **[vendor + independent co-byline, 2026-10-20] Vals post:** evaluation run 2026-10-19; "Keenable Pro" with GPT-5.6 Sol scored 49.08%, "ranks first overall"; +5.50 points vs native search, +3.84 vs Exa; Finance 53.9% vs Exa 52.0%; Legal 44.2% vs 38.5%; cost per task $8.84 vs $18.97 ("53% lower total task cost, including both model inference and search fees"); duration 6m35s vs 8m51s (~26% shorter). The post offers no explanation of why. — [Keenable blog](https://keenable.ai/blog/keenable-vals-web-search-index)
- **[vendor, 2026-07-26] Gradium post:** "Keenable returns web retrieval in under 200ms"; retrieval is "fast enough to sit inside the agent's reasoning loop instead of interrupting it"; most search APIs take "seconds". No p50/p95, no mechanism, no founder quotes. — [Keenable blog](https://keenable.ai/blog/natural-conversation-live-retrieval-keenable-search-with-gradium)
- **[vendor, fetched 2026-11-05]** Every fetched post shows page metadata "Nov 3, 2026, 1:46 PM UTC" alongside its byline date, i.e. the blog was re-rendered on 2026-11-03; byline dates are used here. — [example](https://keenable.ai/blog/keenable-vals-web-search-index)
- **[vendor, fetched 2026-11-05]** The CLI SKILL.md documents result fields `published_at` and `acquired_at`, filters `--published-after/-before` and `--acquired-after/-before`, and point-in-time search `--query-time`; keyless use shares a per-IP pool of 1,000 requests/hour, logged-in use includes 100,000 free requests/month. — [app.keenable.ai/SKILL.md](https://app.keenable.ai/SKILL.md)

### Inferences
- The Dynamic Snippets mechanism is a small discriminative token classifier, not a generative LLM summariser; that is why it can be query-conditioned yet "add no latency" at a 200ms p95. It is the one fully disclosed technical component, and it directly targets agent context cost (the "tokens the model spends reading retrieved content" framing in the Baseten post).
- The `acquired_at` field and `--query-time` filter imply the index stores per-document acquisition timestamps and retains versions (the homepage's "Time Machine" early-access product). This is a structural difference from APIs that only expose published dates.
- The "per-task index structures" phrase in the assignment does not correspond to a Keenable blog post; it appears to derive from the TechCrunch paraphrase in KQ1.

### Gaps
- No blog post on crawler design, index structure, ranking model, or latency engineering exists as of 2026-11-05; the cognee and Lightpanda posts were not fetched (budget) and are integration announcements by title.
- NEEDLE score figures are in charts not present in the extracted text (and are covered by the other researcher).
- Whether the snippet classifier runs at query time over cached page text, and what model family it is, is undisclosed.

- Index-size (100B+) plus "started six months ago" (NEEDLE post) implies a crawl rate on the order of >10B pages/month during 2026; this is arithmetic on vendor claims, not a sourced figure.

### Inferences
- The practitioner consensus, such as it is, matches the independent AA data: Keenable wins on latency and price, is competitive-but-not-top on quality in AA's harness, and its own NEEDLE benchmark is viewed with the usual vendor-benchmark skepticism.
- The HN critique that NEEDLE's "ultimate" pooling cannot reward documents only one engine finds was answered by the authors (the engine is in the pool, so unique relevant results earn full nDCG credit). That answer is methodologically sound for nDCG against a pooled ideal, but pooled relevance judging still cannot reward relevant documents that no engine in the pool returned.
- The low HN engagement on the Show HN (12 points) versus the SELECT showcase (60 points) suggests the product-shaped demos travel further than the API itself among developers.

## KQ6 (key question). Concretely, beyond marketing, what explains Keenable's low latency and strong agent-benchmark results, and how does it differ from Exa's embedding-first design?

### Takeaway
Four disclosed, checkable factors explain most of the result: (1) an owned 100B-document crawl/index with per-query search-space narrowing (Styskin), which removes federation hops and gives coverage of rare entities and sec.gov pages; (2) a tiered latency product (realtime p50 ~200ms / p95 <250ms, Pro for quality) that lets agents issue more calls per task; (3) query-time Dynamic Snippets from a token classifier that halve result tokens with no added latency, which Keenable's own runs tie to a 10.7-point BrowseComp gain; (4) agent-oriented operators (site/date/acquired-at/query-time, up to 50 results per call) that fit agents' burst-and-refine behaviour. The first-stage retrieval model is undisclosed, so "lexical vs embedding" versus Exa cannot be sourced; the documented difference is that Exa's disclosed design centres on semantic/neural retrieval and multiple depth modes, while Keenable's disclosed design centres on index ownership, latency and context-token reduction.

### Cited Findings
- **[journalist, 2026-08-25]** Styskin: "you need to innovate on how you can narrow the search space based on your query very fast"; index structures tuned per task; 100B+ documents. — [TechCrunch](https://techcrunch.com/2026/08/25/accel-backed-keenable-is-indexing-the-web-for-ai-agents/)
- **[vendor, 2026-08-27]** "Owning the index lets us be aggressive here: p50 is 200ms today, and we're targeting 200ms p95"; "the major factor is index uniqueness" on rare-entity queries; "Some systems appear to share the same index!" — [Keenable blog](https://keenable.ai/blog/needle-the-benchmark-your-search-engine-can-t-memorize)
- **[vendor, 2026-10-15]** Dynamic Snippets: query-conditioned token classifier; 49% smaller production responses; BrowseComp 1.16M→466k tokens and 56.6%→67.3% accuracy; "add no latency"; realtime API "p95 latency of 200ms". — [Keenable blog](https://keenable.ai/blog/keenable-snippets-full-page-cost-reduction)
- **[vendor-affiliated, 2026-08-25]** Lower cost and latency "lets models call search more often"; up to 50 results per query at the flat price vs Exa charging beyond top-10. — [HN](https://news.ycombinator.com/item?id=49435555)
- **[independent, 2026-10-21]** Vals: Sol "searches heavily with either tool, more so with Keenable"; median $3.22 per task with Keenable; 77% of finance citations are SEC filings. — [Vals](https://www.vals.ai/benchmarks/web_search)
- **[independent, ~2026-10; via WebSearch summary]** Artificial Analysis: Keenable realtime average search call 0.34s (fastest on the board); task time 15.1s vs Exa auto 26.2s; quality Exa auto 74 vs Keenable realtime 67. — [Artificial Analysis](https://artificialanalysis.ai/articles/search-api)
- **[vendor, fetched 2026-11-05]** `acquired_at` and `--query-time` fields/filters (point-in-time search). — [SKILL.md](https://app.keenable.ai/SKILL.md)
- **[vendor, via WebSearch summary, undated]** Exa describes itself as combining "a custom web index, semantic search, and full page text" with search types instant / fast / auto / deep / deep-reasoning trading latency for depth. — [Exa](https://exa.ai/alternatives/exa)

### Inferences
- Latency: the sub-250ms p95 is plausible only for an owned, co-located index with no federation and with snippet generation done by a small classifier rather than an LLM; the "realtime" mode likely skips expensive reranking that the "Pro" mode (used on Vals) keeps. Keenable has not confirmed this split.
- Benchmark strength on Vals is best explained by coverage of sec.gov filing pages and long result lists under operator-style queries, combined with per-call cost low enough that the agent could search more without blowing the budget. Benchmark relative weakness on AA (67 vs Exa 74) was measured in realtime mode, the latency-optimised tier, so the two independent benchmarks are not measuring the same Keenable configuration.
- Versus Exa: Exa's public design is embedding/neural-first with depth modes; Keenable's public claims never mention embeddings and emphasise index ownership, uniqueness on rare entities, operators, time-travel and token reduction. The honest conclusion is that Keenable competes on the index and the serving path, not (so far as disclosed) on a different retrieval model.

### Gaps
- Keenable has not disclosed its first-stage retrieval (lexical, dense, hybrid), its ranker training signal beyond "agent trajectories", or its reranking stack; the "Pro" vs "realtime" internal difference is undocumented.
- Exa's own architecture docs were not fetched in this task (another researcher's scope); the Exa characterisation above rests on a search-engine summary of an Exa marketing page.
- No independent latency measurement of Keenable other than AA's 0.34s average call was collected; the 200ms/250ms figures are vendor.
- The link between Dynamic Snippets and the Vals result is an inference; Vals does not report tokens per task.
